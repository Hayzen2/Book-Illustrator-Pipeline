## TECH STACK DECISIONS
### 1. Database Choice: MySQL vs. JSON Files (AI Override)
Gemini proposed using JSON files on the local disk to strictly adhere to the "right-sized solution" constraint, suggesting an in-memory `ConcurrentHashMap` and `ReentrantLock` in Spring Boot to handle concurrent writes. However, I pushed back because if the Spring Boot server crashes or restarts suddenly during a 30-second Gemini API call, the in-memory lock is destroyed. The JSON file would be left in an inconsistent state, making the "nothing stuck forever" recovery requirement impossible to guarantee safely. Finally, I propose my reason of choosing MySQL on this matter to Gemini and landed on it. It provides built-in ACID atomicity, ensuring that state transitions and payload saves are all-or-nothing (Atomicity), while allowing for easy timestamp-based recovery for stranded steps. The cost is the operational overhead: the reviewer must run a Docker Compose file instead of a simple script to initialize the database, a trade-off I accepted for data integrity, concurrency safety and its easy-integration with Spring Boot.

### 2. Database Schema Design (Error Message on Failure) (AI Override)
Gemini's initial schema for step execution tracked basic statuses (`PENDING`, `IN_PROGRESS`, `COMPLETED`, `FAILED`) but there was no way to persist error details. I pushed back because section 4.3 states the pipeline must be **"Resumable: Refresh, logout, or server restart mid-pipeline → reopening the project shows its true state,"** and section 4.4 explicitly requires an **"Error state with a retry button for that step."** Without persisting the error, a user refreshing the page after a failure would just see a generic failed state rather than the specific reason. I landed on adding an `error_message` TEXT column to the `project_steps` table to store the exact error details, which the frontend retrieves to render the error accurately to the user. The cost is a minor increase in database storage and the added backend responsibility to explicitly clear this field to `NULL` upon a retry attempt.

### 3. Database Schema Design (Context-chaining problem) (AI Override)
Gemini initially generated a database schema that only saved the local file path of the book. That means we would need to re-send from the database to the Gemini API model the entire book text for every step. I pushed back because this violates the strict "Cost discipline" requirement which states: **"Send the book's content to Gemini once and reuse it across steps... Do not re-send the full text on every step."** By analyzing the provided Notebook and the Gemini REST API docs, I discovered the Interactions API supports server-side context chaining via `previous_interaction_id`. I forced Gemini to redesign the schema, adding `book_interaction_id` to the `projects` table and `interaction_id` to `project_steps`. We landed on a design where the backend only sends the book once, and subsequent steps simply pass the ID of the previous interaction to maintain context. The cost is slightly more complex state management in the backend (tracking sequential IDs), but it drastically reduces payload size and quota consumption.

### 4. Concurrency Handling Decision: Atomic State Transition vs. Database Locking
Gemini proposed using an Atomic State Transition ("Claim-Check") pattern via a custom `@Modifying` SQL `UPDATE` to prevent duplicate Gemini API calls from double-clicks or multiple tabs (Requirement 4.3). I questioned this approach, asking to compare it against standard Pessimistic and Optimistic locking to ensure it was the optimal choice. Gemini correctly pointed out that Pessimistic locking would hold the database connection open during the 30-second API call, exhausting the connection pool, while Optimistic locking validates at commit time, which risks executing the API call twice before failing. We landed on Gemini's atomic update approach. It will update the status to `IN_PROGRESS` and releasing the DB connection in milliseconds before the external API call even starts. The cost is a slightly more complex service-layer orchestration, as it requires strictly separating the database transaction from the external API execution rather than relying on standard Spring `@Transactional` blocks.

### 5. API Shape and Gemini Integration 
To satisfy the strict "resumable" and "per-item progress" requirements, I asked Gemini to propose the internal REST API shape. Gemini proposed a unified execution endpoint (`POST /api/projects/{id}/steps/{stepName}/execute`) returning `202 Accepted`, paired with a single "Fat GET" endpoint (`GET /api/projects/{id}`) that aggregates all project state, characters, and errors into one payload. I accepted this design as it perfectly supports our polling strategy and ensures the atomic lock is uniformly applied. For the external Gemini integration, following the assessment's explicit hint, I decided to use Spring `RestClient` to make raw HTTP calls directly to the `v1beta/interactions` endpoint, explicitly avoiding the Java SDK, while choosing `gemini-2.5-flash` and `gemini-2.5-flash-image` as the current models. The cost is a slight data over-fetching on the frontend with the Fat GET, and the backend effort to manually parse Gemini JSON responses, but it guarantees flawless state recovery and full context-chaining capabilities.

### 6. Conntectipn type: Real-Time Streams vs. Short Polling 
To achieve the "per-item progress" requirement (showing portraits as they land), I considered implementing WebSockets or Server-Sent Events (SSE) since they were mentioned in the assessment's Bonus section. However, to respect the core "Right-sized solution" rule and the estimated ~16-hour budget, I asked Gemini to compare their trade-offs against HTTP short-polling. Gemini advised against WebSockets/SSE, highlighting that handling a page refresh (F5) with stateful connections requires complex reconnection logic, which actively ruin the strict "Resumability" requirement. I agreed and I landed on a stateless approach: executing the AI calls in a Spring `@Async` background thread and using simple 2-second HTTP short-polling on the frontend via a unified "Fat GET" endpoint (`GET /api/projects/{id}`). The cost is accepting ~15 lightweight HTTP requests over a 30-second window and up to a 2-second visual delay, but it keeps the system drastically simpler, highly resilient, and perfectly aligned with the project scope.
